# Creator and administrator analytics

Approved 5 November 2026. Creators see their own videos in Profile > Video analytics. The private web dashboard at /analytics uses the existing Vidoora login. The backend re-reads current database roles and suspension state for every report. ADMIN can filter all creators by their numeric support ID, video UUID and date. The selected admin account is 10000007. Creator filters always compose with the authenticated creator scope, even if a JWT contains a forged/stale ADMIN role claim.

The Android analytics update reports successful viewer-details visits and foreground content playback. Creator self-viewing is excluded. Opens are sessions, starts are sessions that report actual playing content, and a qualified view is at least 30 watched seconds or 90% of a shorter video. Qualified views and completions are deduplicated per video/viewer/day. Daily viewers are estimates. Across date ranges, daily hashes count viewer-days, so the dashboard labels that explicitly. Guest reinstalls and cleared app data can count again. No IP addresses, email addresses, share capabilities or raw guest IDs are stored in analytics sessions.

The device stores a random first-party viewer identifier in encrypted preferences. The server stores a day-scoped HMAC of the authenticated user ID or guest identifier using a purpose-separated key input. Watch counters exclude pauses, buffering, seek distance, ad playback and background time. Heartbeats are cumulative and duplicates add no time. The server bounds reports by elapsed wall time, accepts cumulative retry counters bounded by session wall time, expires sessions after six hours and retains raw session records for 90 days. This is app-reported product analytics, not independently verified audience measurement or financial/ad accounting. Cumulative counters recover missed reports and pause/exit flushes send the final watched seconds. Process termination before delivery can still omit unsent time.

Analytics accepts at most 60 event requests per minute per signed-in user/guest identifier in a bounded process-local limiter. A per-video daily insertion check limits sessions to about 20,000, with a small possible concurrency overrun. These are storage and retry safeguards, not bot-proof unique-human detection. Retention cleanup deletes up to 5,000 expired sessions per hour while events arrive.

Dates use Asia/Kolkata. Report ranges are up to 31 days within the retention window. Results show complete range totals and daily totals, the top 100 videos, and the top 100 creators for admins. Videos are ranked by qualified views and then opens. Deleted videos retain their historical totals until retention cleanup. Original private/shared access and blocking checks apply before collecting any event. Revoking a link prevents further events for that link.

The web dashboard keeps tokens in memory, has no external scripts, renders titles with textContent, and requires a new login after access-token expiry. Logout revokes the refresh session through the existing API. Analytics responses are no-store and analytics request paths are excluded from application access logging. Review the app's privacy policy/Data safety disclosure for first-party app-interaction analytics before releasing the tracking-enabled Android build.

New schema V17 adds video_analytics_sessions. Existing video views_count is not used or retroactively converted. Counts begin only after the new backend and Android build are installed. Physical-device and live deployment results must be recorded separately from local tests.
